Host Intrusion Detection & Integrity Monitoring Stack for SecureBlue OS

This is a host-based intrusion detection & integrity monitoring stack designed to detect unauthorized system modifications through two complementary layers of defense.

What it does

The stack consists of five components working together:

  • Audit rules: Real-time kernel monitoring of system configuration changes. They watch identity stores, polkit configuration, linker preloads, SSH settings, firewall rules, systemd units & network configuration. They catch the exact moment a file is modified via syscall interception.
  • AIDE: Daily cryptographic scan of the entire filesystem integrity. It scans the entire filesystem daily, comparing current files against a trusted cryptographic baseline. It detects changes regardless of whether auditd was running when they occurred.
  • SUID scanner: Detects unauthorized privileged binaries in mutable paths. It baselines all setuid/setgid binaries found in mutable paths (/etc, /var, /home, /usr/local). On rpm-ostree systems, the baseline is typically zero because all standard SUID binaries reside in the immutable /usr tree; any new appearance is suspicious.
  • Canary files: Decoy files placed in monitored locations that trigger alerts on unauthorized access. Any read, write, or execute access generates an audit event, acting as a tripwire for reconnaissance.
  • Daily review: Automated journal summary of all security events. It runs automatically each day, querying audit logs, AIDE status & SUID drift & outputs a concise summary to the system journal.

Why both AIDE & auditd are required

Both tools are required because they cover different threat models:

  • Real-time detection: auditd intercepts syscalls as they happen, alerting instantly when a watched file is modified. AIDE only reports changes during its scheduled scan.
  • Full filesystem coverage: auditd only monitors paths you explicitly configure. AIDE scans the entire filesystem, catching tampering in locations you might have forgotten to watch.
  • Offline change detection: If auditd is stopped or the system is suspended during a change, auditd misses it entirely. AIDE compares against a stored baseline & reports any deviation, regardless of when it happened.
  • Overlayfs compatibility: On rpm-ostree systems, /etc & /usr are overlay filesystems. auditd's inode-based watches can fail to trigger on overlay layers. AIDE hashes the actual file content, bypassing filesystem abstraction entirely.
  • Cryptographic proof: auditd logs that an event occurred, but provides no proof of what the file looked like before or after. AIDE stores SHA-256 & SHA-512 fingerprints, providing tamper-evident evidence of file state.

Together, they ensure no persistent tampering goes unnoticed, whether through a live syscall or a quiet file swap while the system sleeps.

Why this belongs in SecureBlue

I built this solution because I noticed SecureBlue stops attacks well, but doesn't notify you if and when one gets through.

What SecureBlue already does well

  • Immutable base system (rpm-ostree)
  • Hardened kernel, malloc & compiler flags
  • Usbguard, MAC policies & network hardening
  • Minimal attack surface through decluttering

What it lacks, and why this stack matters

SecureBlue's approach The gap What this stack adds
Preventive hardening No detection of successful bypasses Post-exploitation visibility
Immutable /usr Mutable /etc, /var, /home remain exposed Integrity monitoring for mutable paths
Policy enforcement No audit trail of policy violations Tamper-evident logging
Boot-time security No runtime change detection Continuous monitoring between boots

Specific scenarios this catches that SecureBlue alone misses

  • An attacker with physical access modifies /etc/passwd to add a backdoor account: auditd catches the syscall in real-time, AIDE catches it on next scan
  • Malware drops a SUID binary in /home or /var/tmp: SUID scanner alerts on next run
  • Someone edits polkit rules to weaken run0: audit rule fires instantly
  • A compromised process reads canary files during reconnaissance: audit log shows the exact PID & timestamp

Why it belongs in SecureBlue specifically

  • rpm-ostree's overlayfs makes traditional auditd unreliable on /etc & /usr: AIDE's content hashing bypasses this entirely
  • Statically linked AIDE avoids hardened_malloc conflicts: no security trade-offs, no bypasses needed
  • The SUID baseline being ~0 on rpm-ostree is a unique advantage; any deviation is immediately suspicious, unlike traditional distros where dozens of SUID binaries are normal

Why this matters

SecureBlue hardens well, but hardening without detection ultimately leaves you blind to successful bypasses. If someone edits /etc/passwd or drops a SUID binary in /var/tmp, you need to know. Important to note: This stack is not a replacement for SecureBlue's prevention; it is the other half of defense in depth.

Some will call it scope creep, to which I would say, fair enough. But I would rather have logs I never read than miss a compromise I could have caught. The tools are cheap, the baseline is zero and the setup will take you just one afternoon. If you install it just to ignore the daily review, that's on you. The architecture is sound.

Phase 0: Build Static AIDE

CRITICAL: SecureBlue's hardened_malloc breaks dynamically linked AIDE. The standard Fedora package segfaults during database operations. Building a statically linked AIDE eliminates the conflict: the binary bundles its own allocator & ignores the system's LD_PRELOAD & malloc hooks. This preserves hardened_malloc for all other processes.

Build complexity: Fedora 44 does not ship static library archives (.a files) for nettle, pcre2, or zlib in standard repositories. The build must compile these dependencies from source, then statically link AIDE against them. This requires only bison & flex from Fedora; all other dependencies are built from upstream source.

Nettle 4.0 compatibility: AIDE 0.19.3 was written for nettle 3.x. Nettle 4.0 changed the nettle_hash_digest_func API from 3 arguments to 2. This guide applies a one-line patch to src/md.c before building. The patch removes the obsolete length parameter from the digest call. If you prefer not to patch AIDE, use nettle 3.10.2 (the last 3.x release) instead; the fallback URL is provided.

Why static linking is acceptable here

Static linking AIDE does not weaken your system. It isolates a compatibility issue.

The problem: hardened_malloc breaks dynamically linked AIDE during large database operations. The segfault is a compatibility bug, not an AIDE vulnerability.

The fix: The static binary bundles its own allocator and ignores LD_PRELOAD. hardened_malloc never loads into AIDE's address space. Every other process keeps hardened_malloc.

The risk: AIDE uses a standard allocator. But it is non-network-facing, short-lived, and only reads local files that have already passed through kernel and filesystem checks. The alternative is a non-functional tool. I will take a working integrity scanner with an isolated allocator over a broken one every time. The trade-off is documented.

Phase 2: Audit Rules

CRITICAL: SecureBlue's run0 wrapper strips /usr/sbin & /sbin from PATH for security. All audit tools live in /usr/sbin. Therefore, every audit command in this phase must use absolute paths. Copy-pasting standard commands will fail with "command not found." This guide uses absolute paths exclusively; do not abbreviate.

1. Create base monitoring rules

Note: The $(whoami) command expands to your actual username at file creation time because the heredoc uses double quotes. Verify the output matches your username. 
# Create audit rules defining watched paths & their monitoring keys
# -p wa: watch for writes & attribute changes
# -k <key>: tag events for ausearch filtering
# Double quotes allow $USER to expand; run0 preserves your original username
run0 /usr/bin/tee /etc/audit/rules.d/99-secureblue-custom.rules << EOF
# Identity & authentication stores
-w /etc/passwd -p wa -k identity_changes
-w /etc/shadow -p wa -k identity_changes
-w /etc/group -p wa -k identity_changes
-w /etc/gshadow -p wa -k identity_changes

# Dynamic linker hijacking

-w /etc/ld.so.conf.d/ -p wa -k linker_hijack

4. Create privilege escalation rules

Detection gap: Base rules watch configuration files but miss runtime escalation vectors: execution of elevation binaries, account manipulation syscalls, kernel module loading, eBPF attachment & SUID bit changes. These rules close that gap. The SUID rule excludes unset auid to avoid false positives from system daemons. 
# Create dedicated privilege escalation rules file
# These load before 99-secureblue-custom.rules via numeric ordering (98-privesc.rules)
run0 /usr/bin/tee /etc/audit/rules.d/98-privesc.rules << 'EOF'
# Privilege Escalation Detection: SecureBlue
# Elevation binaries
-w /usr/bin/run0 -p x -k privesc_run0
-w /usr/bin/pkexec -p x -k privesc_pkexec
-w /usr/bin/passwd -p x -k privesc_passwd

# Account management
-w /usr/sbin/useradd -p x -k privesc_account
-w /usr/sbin/usermod -p x -k privesc_account
-w /usr/sbin/userdel -p x -k privesc_account
-w /usr/sbin/groupadd -p x -k privesc_account
-w /usr/sbin/groupmod -p x -k privesc_account
-w /usr/sbin/groupdel -p x -k privesc_account

# Authentication configuration
-w /etc/pam.d/ -p wa -k privesc_pam
-w /etc/security/ -p wa -k privesc_security

# SUID/SGID bit manipulation by non-system users
# auid!=-1 excludes system daemons (systemd-resolve, etc.) that run with unset auid
-a always,exit -F arch=b64 -S chmod -S fchmod -S fchmodat -F auid>=1000 -F auid!=-1 -k privesc_suid

# Kernel module & eBPF loading
-a always,exit -F arch=b64 -S init_module -S finit_module -S delete_module -k privesc_kmod
-a always,exit -F arch=b64 -S bpf -k privesc_bpf

# Capability manipulation
-w /usr/sbin/setcap -p x -k privesc_caps

# Persistence vectors
-w /etc/cron.d/ -p wa -k privesc_persist
-w /etc/cron.daily/ -p wa -k privesc_persist
-w /etc/cron.hourly/ -p wa -k privesc_persist
-w /etc/cron.weekly/ -p wa -k privesc_persist
-w /etc/cron.monthly/ -p wa -k privesc_persist

Phase 4: SUID Scanner

Baseline timing matters: The scanner captures all mutable SUID binaries at first run as "normal." If you later layer packages that install to /opt or /usr/local, those new SUID binaries will trigger false positive alerts. After installing any such package, re-run run0 /usr/local/bin/suid-scanner to re-establish baseline. The script will overwrite baseline.txt with the new state.

1. Create the scanner script

Script logic: On first run, it copies current.txt to baseline.txt. On subsequent runs, it diffs against baseline. The 2>/dev/null suppresses permission denied errors from restricted paths like /var/lib/private. If you need to audit those paths, run with elevated permissions or adjust the find command. 
# Create scanner that detects new setuid/setgid binaries in mutable paths
# /usr is excluded because it is immutable on rpm-ostree; any SUID there is vendor-trusted
run0 /usr/bin/tee /usr/local/bin/suid-scanner << 'EOF'
#!/bin/bash
set -euo pipefail

BASELINE="/var/lib/suid-scanner/baseline.txt"
CURRENT="/var/lib/suid-scanner/current.txt"
DIFFOUT="/var/lib/suid-scanner/diff.txt"

# Scan mutable paths only. /boot included because it is not immutable on all deployments.
/usr/bin/find /etc /var /opt /home /usr/local /boot -type f \( -perm -4000 -o -perm -2000 \) 2>/dev/null | /usr/bin/sort > "$CURRENT"

if [[ ! -f "$BASELINE" ]]; then
    /usr/bin/cp "$CURRENT" "$BASELINE"
    /usr/bin/echo "Baseline established: $(/usr/bin/wc -l < "$CURRENT") mutable SUID/SGID binaries"
    exit 0
fi

if ! /usr/bin/diff -q "$BASELINE" "$CURRENT" > /dev/null 2>&1; then
    /usr/bin/diff "$BASELINE" "$CURRENT" > "$DIFFOUT" || true
    /usr/bin/echo "ALERT: SUID/SGID drift detected"
else
    : > "$DIFFOUT"
fi
EOF
run0 /usr/bin/chmod +x /usr/local/bin/suid-scanner

2. Create systemd timer

# Service unit for the scanner
run0 /usr/bin/tee /etc/systemd/system/suid-scanner.service << 'EOF'
[Unit]
Description=Scan for new SUID/SGID binaries

[Service]

EOF

# Timer unit: runs daily, persists across missed intervals (e.g., system was off)
run0 /usr/bin/tee /etc/systemd/system/suid-scanner.timer << 'EOF'

[Timer]

Phase 5: Daily Review Script

Journal retention: On a clean SecureBlue install, journald defaults to Storage=auto with MaxFileSec=1month, which is adequate. However, if your system has Storage=volatile or aggressive vacuuming configured, audit events may be lost before the daily review runs. Verify /etc/systemd/journald.conf & ensure /var/log/journal/ exists for persistent storage. The review script cannot summarize events that have already been deleted.
PATH handling in script: The script sets PATH internally because it runs as a systemd service where PATH may be minimal. All audit tool calls use absolute paths to avoid any dependency on PATH resolution. This preserves SecureBlue's hardening intent while ensuring the script functions correctly in restricted environments. 
# Create the daily review script that summarizes all security events
run0 /usr/bin/tee /usr/local/bin/audit-review << 'EOF'
#!/bin/bash
# Restore full PATH for utility commands, but audit tools use absolute paths below
PATH=/usr/sbin:/usr/bin:/sbin:/bin
export PATH

echo "=== AUDIT SUMMARY ==="
# Count active rules using absolute path for auditctl
# If 0, auditd is down or rules were lost.
echo "Active rules: $(/usr/sbin/auditctl -l 2>/dev/null | /usr/bin/wc -l)"

Phase 7: Remove Build Dependencies

CRITICAL: The build dependencies installed in Phase 0 (bison, flex) expand the attack surface. Compilers & build tools are prime targets for privilege escalation if an attacker gains local access. Remove them immediately after AIDE is verified working. The static AIDE binary & its database remain fully functional without these tools.
Reboot required: rpm-ostree uninstalls packages into a new deployment. The removal only becomes active after reboot. Until then, the tools remain available in the running system.

Troubleshooting

These are issues I personally encountered while building this stack on my machine. They may not match your exact error, but the fix patterns should transfer.

AIDE segfaults during database operations

Symptom: run0 /usr/local/bin/aide --init or --check crashes with a segfault or memory error.
Cause: SecureBlue's hardened_malloc conflicts with dynamically linked AIDE. The Fedora package bundles glibc malloc hooks that hardened_malloc overrides.

Fix: Build AIDE statically from source as described in Phase 0. The static binary ignores LD_PRELOAD and uses its own bundled allocator. Verify with:

/usr/bin/ldd /usr/local/bin/aide
# Expected: "not a dynamic executable" or empty output
LD_PRELOAD=/usr/lib64/libhardened_malloc.so /usr/local/bin/aide --version
# Expected: runs normally without crash

auditctl reports "No rules" after augenrules --load

Symptom: run0 /usr/sbin/augenrules --load prints "No rules" followed by warnings.
Cause: augenrules checks the legacy /etc/audit/audit.rules file first. If it is empty, it reports "No rules" even while successfully loading rules from /etc/audit/rules.d/. The warnings about "Old style watch rules are slower" confirm the rules did load.

Fix: Ignore the "No rules" message if you see the style warnings. Verify with run0 /usr/sbin/auditctl -l | /usr/bin/wc -l or run0 /usr/sbin/ausearch -k privesc_run0 -ts recent.

systemctl restart auditd fails with "Operation refused"

Symptom: run0 systemctl restart auditd returns "Operation refused, unit auditd.service may be requested by dependency only."
Cause: SecureBlue hardens the auditd unit to refuse manual start/stop. This prevents accidental disruption of the audit subsystem.

Fix: Do not restart auditd. Load rules directly into the kernel with run0 /usr/sbin/auditctl -R /etc/audit/rules.d/99-privesc.rules. The daemon is already running; you only need to refresh the kernel configuration.

systemd-resolve floods privesc_suid audit logs

Symptom: run0 /usr/sbin/ausearch -k privesc_suid -ts recent shows dozens of fchmod events from systemd-resolve with auid "unset".
Cause: The auid>=1000 filter treats unset auid (4294967295) as a large unsigned integer, so it passes the filter. systemd-resolve sets permissions on its runtime files during normal operation.

Fix: Add -F auid!=-1 to the SUID rule in /etc/audit/rules.d/98-privesc.rules as shown in Phase 2 Step 4. Reload with run0 /usr/sbin/auditctl -R /etc/audit/rules.d/98-privesc.rules.
